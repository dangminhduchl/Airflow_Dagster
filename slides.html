@dag(dag_id="invoice_multipage_pdf_dag", schedule=None, catchup=False)
def invoice_multipage_pdf_dag():

1. Trói Chặt Vào Task ID

Hàm rẽ nhánh phải return chuỗi string "extract_pages", đổi tên task là code bị gãy.

2. XCom Ẩn Dưới Nền

Dữ liệu giữa các task được ngầm nạp (INSERT) vào bảng xcom trong PostgreSQL.

3. TriggerRule Phức Tạp

Nếu không set NONE_FAILED_MIN_ONE_SUCCESS, cả pipeline sẽ bị fail vì nhánh rác bị skip.

Hãy mổ xẻ code Airflow mà chúng ta vừa viết: Thứ nhất: @task.branch bắt buộc hàm phải trả về string chứa tên của task_id tiếp theo. Nghĩa là code logic nghiệp vụ bị trói cứng vào tên của task trong DAG. Thứ hai: Để 4 nhánh chạy song song nhưng không bị lỗi khi một vài nhánh không có trang nào, ta phải cấu hình TriggerRule.NONE_FAILED_MIN_ONE_SUCCESS. Nếu quên dòng này, toàn bộ pipeline sẽ bị treo hoặc báo fail do cơ chế mặc định all_success. Thứ ba: Làm sao dữ liệu đi từ hàm này sang hàm kia? Đó là qua cơ chế XCom.

Cấu Tạo 4 Thành Phần Trụ Cột Của Airflow

┌────────────────────────────────────────────────────────┐ │ APACHE AIRFLOW │ │ │ │ ┌───────────────┐ ┌───────────────┐ │ │ │ Webserver │ │ Scheduler │ │ │ │ (Flask UI) │ │ (Heartbeat) │ │ │ └───────┬───────┘ └───────┬───────┘ │ │ │ │ │ │ ▼ ▼ │ │ ┌──────────────────────────────────────────────┐ │ │ │ Metadata Database (PostgreSQL / MySQL) │ │ │ │ (DAG Runs, Task Instances, XCom, Variables)│ │ │ └──────────────────────────────────────────────┘ │ │ ▲ │ │ │ Báo cáo trạng thái │ │ ┌──────────┴──────────┐ │ │ │ Executor / Worker │ │ │ │ (Celery / K8s Pods)│ │ │ └─────────────────────┘ │ └────────────────────────────────────────────────────────┘
1. Scheduler (Bộ não điều phối)

Quét file Python liên tục, xác định task nào sẵn sàng chạy và ném vào hàng đợi (Queue).

2. Metadata DB (Nút thắt cổ chai)

Mọi thành phần đều phụ thuộc vào DB này. Nếu DB nghẽn hoặc lock bảng, toàn bộ hệ thống tê liệt.

3. Webserver & Worker

Webserver chỉ đọc DB để vẽ UI. Worker nhận task chạy trong môi trường riêng rồi ghi log & kết quả về DB.

Để hiểu vì sao Airflow gặp khó khăn với các bài toán dữ liệu hiện đại, ta phải nhìn vào cấu tạo 4 thành phần này. Airflow ra đời năm 2014, thời điểm mà người ta chỉ cần một công cụ Cronjob mạnh mẽ để kích hoạt các job Hadoop/Hive chạy ban đêm. Mọi giao tiếp giữa Scheduler, Webserver và Worker đều đi qua một chiếc 'nút cổ chai' duy nhất: Metadata Database PostgreSQL.
PHẦN 3: PHÂN TÍCH CODE & CẤU TẠO AIRFLOW

Cách Chạy Ngầm Cốt Lõi: DAG Parsing Loop & XCom

1. Vòng Lặp Phân Tích File (DAG Parsing Loop)
  • Scheduler không lưu sẵn đồ thị trên RAM.
  • Cứ mỗi 30 giây, một tiến trình con (DAG File Processor) đọc và biên dịch lại toàn bộ code Python trong thư mục dags/.
  • Nếu developer lỡ tay gọi 1 API HTTP hoặc import thư viện OCR nặng ở tầng ngoài $\rightarrow$ Scheduler bị treo CPU 100%!
2. Cơ Chế Luân Chuyển Dữ Liệu XCom
  • Task A: return extracted_data
  • Airflow serialize dict/list thành chuỗi JSON/Pickle.
  • Thực hiện lệnh: INSERT INTO xcom VALUES (...) vào Database PostgreSQL.
  • Task B: ti.xcom_pull() $\rightarrow$ SELECT ... FROM xcom.
  • Nếu dữ liệu lớn (ảnh hóa đơn, DataFrame to) $\rightarrow$ PostgreSQL bị tràn bộ nhớ!
Vòng Đời Trạng Thái Của 1 Task Instance
NONE ──► SCHEDULED ──► QUEUED ──► RUNNING ──► SUCCESS / FAILED / SKIPPED
Khi một task return về dữ liệu trong Airflow, dữ liệu đó bị biến thành chuỗi text và ném thẳng vào database PostgreSQL của hệ thống. Nếu danh sách hóa đơn lớn hoặc chứa file ảnh base64, database của Airflow sẽ nhanh chóng bị phình to (bloat), làm chậm toàn bộ cụm điều phối!
PHẦN 4: HẠN CHẾ AIRFLOW & DAGSTER CÓ GÌ MỚI?

Hạn Chế 1: "Mù Dữ Liệu" (Data Blindness)

🔴 Nỗi Đau Airflow: Task-Centric
  • Chỉ quan tâm tiến trình: Task bóc tách hóa đơn chạy xong trả về 0 bản ghi $\rightarrow$ Airflow vẫn báo XANH LÁ CÂY (`SUCCESS`).
  • Kế toán không biết dữ liệu bị rỗng cho đến khi mở báo cáo tài chính cuối tháng.
  • Không có khái niệm "Data Version", không quản lý vòng đời tài sản dữ liệu.
🟢 Dagster Giải Quyết: Software-Defined Asset (SDA)
  • Đổi câu hỏi từ: "Chạy task gì?" sang "Tạo ra tài sản dữ liệu gì?".
  • Mỗi asset khai báo rõ: Schema, phân vùng (partition), metadata số lượng dòng, tổng tiền, thời gian cập nhật.
  • Giao diện theo dõi trung thực: Nhìn vào là biết ngay hóa đơn tháng 3 đã có số liệu hay chưa!
💡 So Sánh Triết Lý

Airflow quản lý hành động (Verbs - Action). Dagster quản lý kết quả dữ liệu (Nouns - Data Assets). Với doanh nghiệp, dữ liệu đúng mới là giá trị cuối cùng.

Điểm hạn chế đầu tiên sinh ra từ cấu tạo Task-centric: Airflow hoàn toàn 'mù' về dữ liệu. Với kế toán, họ không cần biết bạn chạy bao nhiêu Task, họ chỉ cần biết: 'Hóa đơn tháng 3 đã sẵn sàng chưa và số liệu có chuẩn không?'. Dagster đưa Dữ liệu trở thành công dân hạng nhất, phản ánh trung thực giá trị nghiệp vụ.

Hạn Chế 2: Cực Hình Khi Viết Test & Local Debug

🔴 Nỗi Đau Airflow: Dính Chặt Vào Database
  • Hàm Python của Airflow bị "ô nhiễm" bởi context, ti, xcom_pull.
  • Chạy pytest đơn thuần sẽ văng lỗi KeyError: 'ti'.
  • Muốn Integration Test cả DAG: Bắt buộc phải khởi tạo SQLite/PostgreSQL, chạy airflow db migrate nặng nề trong CI/CD.

  • Unit test: Gọi thẳng hàm như code Python lớp 1: extracted_invoice_pages(mock_input).
  • Integration test: Dùng materialize([asset1, asset2]) chạy hoàn toàn trong bộ nhớ RAM, KHÔNG CẦN DATABASE, KHÔNG CẦN SERVER!

Hạn Chế 3: Nghẽn Cổ Chai XCom & Ô Nhiễm Code Lưu Trữ

🔴 Nỗi Đau Airflow: Dữ Liệu Bị Ép Qua DB
  • XCom lưu vào Postgres $\rightarrow$ Dung lượng bị bóp nghẹt vài MB.
  • Muốn lưu file to (PDF, ảnh scan, Parquet): Developer phải tự tay viết code upload S3/MinIO, rồi truyền chuỗi URL qua XCom.
  • Hậu quả: Code logic nghiệp vụ bị trộn lẫn với code hạ tầng lưu trữ.
🟢 Dagster Giải Quyết: I/O Manager (Cắm - Rút)
  • Tách rời 100% giữa Logic tính toán và Vị trí lưu trữ.
  • Hàm Python chỉ làm toán thuần: return invoice_summary.
  • Production: I/O Manager tự đẩy lên S3 / MinIO / PostgreSQL.
  • Unit Test: I/O Manager tự giữ trong RAM (In-Memory).
Lợi Ích Của Nguyên Lý Dependency Injection

Khi chuyển đổi kho lưu trữ từ MinIO sang Ceph hay S3, lập trình viên không phải sửa bất kỳ dòng code nào trong các hàm Asset. Chỉ cần đổi 1 dòng cấu hình I/O Manager!

I/O Manager của Dagster là một cuộc cách mạng về thiết kế phần mềm (Dependency Injection). Lập trình viên chỉ cần return df hoặc return invoice_dict. Việc lưu nó vào MinIO, S3 hay Postgres là do I/O Manager đảm nhận bên ngoài. Khi test, ta rút S3 ra và cắm RAM vào, cực kỳ linh hoạt.

Hạn Chế 4: Monolithic Parsing & Rủi Ro Sập Cụm

🔴 Nỗi Đau Airflow: Dễ "Chết Chùm"
  • Scheduler đọc trực tiếp code Python của người dùng vào cùng tiến trình hệ thống.
  • Nếu 1 file DAG bị lỗi cú pháp, gọi thư viện C bị lỗi, hoặc chiếm dụng RAM $\rightarrow$ Làm đứng luôn Scheduler và Webserver.
  • Tất cả các team phải dùng chung 1 môi trường Python (Dependency Hell).
🟢 Dagster Giải Quyết: gRPC Out-of-Process & Daemon
  • Hệ thống tách làm 2 tầng hoàn toàn độc lập:
    • Hạ tầng quản lý: Dagster Webserver + Dagster Daemon.
    • Code người dùng: Chạy trong các Container riêng (Code Locations) kết nối qua gRPC.
  • Code lỗi cú pháp hay sập container $\rightarrow$ Web UI vẫn sáng đèn, báo lỗi cách ly an toàn!
Ý Nghĩa Sống Còn Trên Cụm Kubernetes On-Premise

Team Hóa đơn có thể dùng Python 3.12 + PyMuPDF, trong khi Team AI dùng Python 3.9 + PyTorch. Hai team deploy 2 Pod riêng biệt, không bao giờ lo xung đột thư viện!

Về mặt DevOps và bảo mật hệ thống, kiến trúc tách rời của Dagster ăn đứt Airflow. Trên Kubernetes, mỗi team có thể deploy một Code Location Pod riêng với thư viện Python độc lập. Team Hóa đơn dùng Python 3.12 không sợ bị xung đột thư viện với Team Machine Learning dùng Python 3.9.

Hạn Chế 5: Thiếu Kiểm Định Dữ Liệu Tích Hợp

🔴 Nỗi Đau Airflow: Phải Đẻ Thêm Hàng Tá Task Phụ
  • Airflow không có khái niệm Data Quality tích hợp.
  • Muốn kiểm tra ngân sách hay tính thuế: Developer phải tự tạo thêm check_vat_task, branch_budget_task.
  • Đồ thị DAG bị phình to bởi các task rác kiểm tra, làm luồng nghiệp vụ bị rối rắm.
🟢 Dagster Giải Quyết: First-Class Asset Checks
  • Kiểm định đính kèm trực tiếp vào Asset:
@asset_check(asset=monthly_financial_expense_ledger, blocking=True)
def check_budget_limit_compliance(monthly_financial_expense_ledger: dict):
    total = monthly_financial_expense_ledger.get("grand_total", 0)
    return AssetCheckResult(passed=(0 < total <= 100_000_000))
  • blocking=True: Tự động ngắt luồng tại chỗ nếu phát hiện vi phạm!
Khả Năng Quan Sát Dữ Liệu (Data Observability)

Lịch sử các lần Pass/Fail của Asset Check được lưu lại thành biểu đồ xu hướng theo thời gian, giúp kiểm toán viên đối soát chất lượng dữ liệu tức thì.

Với Airflow, muốn kiểm định dữ liệu ta phải viết các hàm rẽ nhánh phức tạp. Với Dagster, @asset_check là công dân hạng nhất. Nó vừa kiểm tra, vừa ghi nhận điểm số chất lượng (Data Observability), vừa có quyền lực tối cao để chặn đứng pipeline khi có rủi ro tài chính.

Ma Trận So Sánh Kỹ Thuật Tổng Hợp (7 Tiêu Chí)

Tiêu Chí Kỹ Thuật Apache Airflow 2.x Dagster Đánh Giá
1. Triết lý thiết kế Task-Centric (Chạy tác vụ) Asset-Centric (Tài sản dữ liệu) Dagster thắng
2. Khả năng & Tốc độ Test Phụ thuộc DB, chậm, khó mock Pure Function, chạy Pytest trong RAM 0.05s Dagster vượt trội
3. Luân chuyển dữ liệu XCom nghẽn qua Database I/O Manager tách rời lưu trữ Dagster thắng
4. Kiểm soát chất lượng Tự viết task phụ rườm rà Asset Checks tích hợp (blocking=True) Dagster thắng
5. Cách ly hạ tầng (K8s) Chung tiến trình, dễ xung đột thư viện gRPC Out-of-process, cô lập hoàn hảo Dagster thắng
6. Hệ sinh thái & Connector Khổng lồ (hơn 10 năm phát triển) Trẻ hơn nhưng phát triển rất nhanh Airflow thắng
7. Trải nghiệm Developer Nhiều boilerplate, debug khó Chuẩn Software Engineering hiện đại Dagster thắng
Nhìn vào bảng tổng kết 7 tiêu chí: Airflow chỉ còn giữ ưu thế duy nhất về tuổi đời và số lượng connector có sẵn. Trên toàn bộ các khía cạnh về năng suất lập trình, khả năng kiểm thử, độ tin cậy dữ liệu và kiến trúc đám mây On-Premise, Dagster đều vượt trội hoàn toàn.

Định Vị Ứng Dụng: Khi Nào Nên Chọn Ai?

Khi Nào Nên Chọn Apache Airflow?
  • Điều phối hạ tầng chung chung: Bật/tắt máy ảo, trigger job dbt, gửi email báo cáo hàng ngày.
  • Đã có sẵn cụm vận hành ổn định: Doanh nghiệp đã đầu tư hạ tầng và đội ngũ quen thuộc với Airflow nhiều năm.
  • Các job chạy độc lập (Coarse-grained): Không cần truyền dữ liệu lớn giữa các bước, mỗi bước là một job Spark riêng biệt.
Khi Nào Nên Chọn Dagster? (ĐỀ XUẤT SỐ 1)
  • Thay thế AWS Step Functions: Các pipeline xử lý nghiệp vụ phức tạp, phân nhánh nhiều điều kiện và tính toán logic.
  • Data Platform, OCR & AI/LLM: Các quy trình đòi hỏi kiểm soát chặt chẽ chất lượng dữ liệu, đối soát tài chính.
  • Đội ngũ chú trọng CI/CD & Unit Test: Cần test tự động trên máy local và GitHub Actions mà không tốn công dựng DB.
  • Môi trường Kubernetes đa nhóm: Cần cô lập phiên bản Python giữa các phòng ban.
Khuyến Nghị Cuối Cùng Cho Dự Án

Với bài toán di chuyển từ AWS Step Functions về On-Premise: Dagster là giải pháp tối ưu nhất, vừa giúp tái hiện chuẩn xác State Machine vừa nâng tầm văn hóa kỹ nghệ phần mềm của đội ngũ!

Chúng tôi không nói Airflow tệ. Nếu công ty chỉ cần một công cụ kích hoạt dbt hay chạy job Spark hàng đêm, Airflow vẫn dùng tốt. Nhưng với bài toán thay thế AWS Step Functions trên On-Premise: xử lý OCR văn bản, phân loại hồ sơ và kiểm soát rủi ro tài chính, Dagster chính là sự lựa chọn số 1 của tương lai.
