Kính chào anh chị và các bạn. Hôm nay chúng ta sẽ cùng tìm hiểu và so sánh thực chiến hai công cụ điều phối dữ liệu (Data Orchestration) mã nguồn mở phổ biến và mạnh mẽ nhất hiện nay: Apache Airflow và Dagster. Để đánh giá trực quan nhất, chúng ta sẽ xuất phát từ chính bối cảnh các dự án hiện tại của team và giải quyết cùng một bài toán cụ thể.

AWS STEP FUNCTION

✅ PROS
  • Không cần quản lý hạ tầng
  • Auto-scaling
  • Trả phí theo tải
  • Tích hợp sâu với các dịch vụ khác của AWS
❌ CONS
  • Khó Test và Debug ở Local
  • Chi phí tăng vọt khi tải lớn
  • Bảo mật dữ liệu
  • Phụ thuộc vào AWS
Như team mình đều biết, hầu hết các dự án hiện tại đều đang sử dụng AWS Step Functions và AWS Lambda. Ưu điểm không thể phủ nhận: không cần lo hạ tầng, auto-scale cực tốt và trả tiền theo mức dùng. Tuy nhiên nhược điểm là chi phí state transition rất cao khi tải lớn, khó debug/test cục bộ ở local, và bị phụ thuộc chặt vào AWS. Do đó, nếu bài toán đòi hỏi chạy On-Premise hoặc tối ưu chi phí, chúng ta cần tìm giải pháp mới.
Bài toán : BÀI TOÁN: TỰ ĐỘNG BÓC TÁCH & DUYỆT HÓA ĐƠN (PDF → DATA)

📦 1. Phân loại 4 trang hóa đơn (4 Invoice Types)

  • VAT Invoice: Lấy MST, tiền hàng & tiền thuế.
  • Utility Invoice: Lấy Customer ID để đối chiếu điện/nước.
  • Travel Expense Invoice: Lấy Employee ID để hoàn tiền công tác.
  • Retail Receipt (No Tax ID): ⚠️ Gắn cờ cảnh báo: Không duyệt trừ thuế.

⚙️ 2. Luồng xử lý & Điều kiện duyệt

  • Bước 1 (Nhận file): Kiểm tra file chuẩn, không lỗi.
  • Bước 2 (Bóc tách): Tách 4 trang ↔ Đọc dữ liệu theo từng type.
  • Bước 3 (Kiểm tra):
    • Tiền hàng + Tiền thuế có khớp tổng tiền không?
    • Tổng tiền cả xấp có vượt hạn mức (100tr) không?
  • Bước 4 (Kết quả):
    • ✅ Đạt chuẩn: Duyệt ↔ Lưu vào hệ thống.
    • ❌ Vượt hạn mức / Lỗi: Không duyệt ↔ Dừng ngay lập tức!

🔄 1. Bị Ép Re-Parse Liên Tục (30 Giây/Lần)
Scheduler không lưu sẵn cấu trúc trên RAM mà liên tục đọc và biên dịch lại code Python từ đĩa. Nếu lỡ import OCR nặng hay gọi API ngoài hàm → Treo 100% CPU toàn cụm.
🗄️ 2. State Machine Bắn Query DB Dồn Dập
Mỗi bước chuyển trạng thái (None → Scheduled → Queued → Running → Success) đều phải UPDATE vào bảng task_instance của PostgreSQL → Nguy cơ lock bảng khi có hàng nghìn task.
📦 3. Ép Nạp Dữ Liệu XCom Thẳng Vào Postgres
Khi task return dữ liệu, Airflow biến nó thành JSON/Pickle rồi chạy lệnh INSERT INTO xcom. Dữ liệu lớn (ảnh hóa đơn, DataFrame) làm phình to DB và nghẽn I/O.
👁️ 4. Kết Thúc Bằng "Mù Dữ Liệu" Trên UI
Webserver chỉ đọc DB để tô màu ô vuông Xanh/Đỏ. Người điều hành hoàn toàn không biết bên trong có bao nhiêu hóa đơn, bao nhiêu tiền nếu không tự mò vào từng task đọc log.
Kính thưa các anh chị, đây là toàn bộ vòng đời thực thi của 1 task trong Airflow: 1. Khi ta nạp file code, Scheduler phải chạy vòng lặp DAG Parsing Loop mỗi 30 giây để đọc lại code từ đĩa, gây nghẽn CPU nếu có import nặng. 2. Quá trình đổi trạng thái từ Scheduled sang Queued rồi Running phải liên tục bắn câu lệnh UPDATE vào PostgreSQL. 3. Khi task muốn truyền dữ liệu cho task sau, dữ liệu bị nhồi thẳng vào bảng xcom của database, làm phình to DB. 4. Cuối cùng, Webserver chỉ đọc DB để tô màu ô vuông Xanh/Đỏ mà hoàn toàn mù về dữ liệu nghiệp vụ bên trong!

🛡️ 1. Khám Phá Metadata Qua gRPC (Zero Load)
Code người dùng chạy trong tiến trình riêng. Nền tảng chỉ dùng gRPC để hỏi schema và phả hệ lineage, hoàn toàn không nạp code Python của user vào Scheduler.
🚀 2. Chạy Trong Worker Độc Lập (Ephemeral Worker)
Mỗi lần chạy bật một container/pod độc lập thực thi hàm Asset thuần khiết. Code có crash hay OOM thì Daemon và Webserver vẫn an toàn 100%.
💾 3. I/O Manager Độc Lập & Không Đụng DB
Dữ liệu trả về được I/O Manager tự động đẩy thẳng lên S3/MinIO hoặc Snowflake. Database hệ thống chỉ lưu nhật ký sự kiện nhẹ nhàng, không bao giờ bị nghẽn.
🛡️ 4. Khiên Asset Checks Gác Cổng Tại Chỗ
Chiếc khiên kiểm định @asset_check(blocking=True) chạy ngay trong chu trình: nếu vượt ngân sách 100M, ngắt luồng tại chỗ, ghi nhận lý do và cập nhật real-time lên UI.
Bây giờ, hãy nhìn sang toàn bộ vòng đời khởi tạo 1 tài sản trong Dagster: 1. Toàn bộ code xử lý dữ liệu được cô lập trong User Code Server, nói chuyện với nền tảng qua gRPC. Scheduler không cần nạp code nặng. 2. Mỗi lần chạy, Dagster bật một Worker Pod độc lập để tính toán. Code có crash cũng không ảnh hưởng hệ thống. 3. Dữ liệu tính toán xong được I/O Manager đẩy thẳng lên S3 hoặc Snowflake, database chỉ lưu nhật ký sự kiện Event Log cực nhẹ. 4. Ngay trong chu trình chạy, chiếc khiên Asset Checks tự động thẩm định dữ liệu. Nếu vượt ngân sách 100 triệu, nó ngắt luồng tại chỗ và báo đỏ trực tiếp trên giao diện cho cả team cùng thấy!
🏗️ 1. KIẾN TRÚC HẠ TẦNG ON-PREMISE
Ops Overhead
🔴 AIRFLOW (6 THÀNH PHẦN RỜI RẠC) Cồng kềnh & Dễ nghẽn
• Stack: Scheduler + Celery Worker Pool + Redis Queue + Postgres HA + Webserver + Triggerer.
• Nỗi đau đĩa chia sẻ: Bắt buộc dựng NFS/EFS chia sẻ để đồng bộ file dags/ giữa các node.
• Xung đột package: Toàn bộ task chung Python env; 1 team upgrade pandas làm gãy pipeline team khác.
🟢 DAGSTER (CHUẨN KUBERNETES & CLOUD-NATIVE) Tinh gọn & Độc lập
• Stack: Chỉ cần Dagster Webserver + Daemon + PostgreSQL HA (chỉ lưu event metadata nhẹ).
• Lưu trữ đối tượng: Cụm MinIO phân tán làm S3 nội bộ, I/O Manager tự động đẩy/kéo dữ liệu.
• Code Location Pods: Đóng gói Docker riêng, gọi gRPC. Tự do dùng Python 3.10/3.11/3.12 cách ly.
🧪 2. NĂNG LỰC KIỂM THỬ CI/CD & DEVX
Pytest In-Memory
⚠️ Airflow: Rào Cản Lớn Khi Viết Unit Test & CI/CD
• Task gắn chặt với ti, context, dag_run → Rất khó mock dữ liệu cục bộ.
• Muốn test phải dựng Docker Compose & migrate Postgres (mất 3-5 phút) → Không thể tích hợp Git Hook.

⚙️ 3. KHI NÀO NÊN CHỌN APACHE AIRFLOW?
Hạ Tầng Sẵn Có
🖥️ Điều phối hạ tầng chung: Bật/tắt máy ảo, trigger job dbt snapshot, gửi email cảnh báo, dọn log hệ thống định kỳ.
⚡ Tác vụ thô độc lập (Coarse-grained): Kích hoạt các job Spark, Trino, Flink chạy riêng lẻ, không cần trao đổi data phức tạp.
🏢 Đã đầu tư cụm On-Premise ổn định: Đã có sẵn cụm VM/Celery với đội Ops quen bảo trì 6 thành phần & đĩa mạng NFS.
⏱️ Kiểm thử truyền thống qua DB: Chấp nhận test phụ thuộc Database (dựng Docker Compose 3 - 5 phút/lần).
📌 Tóm lại: Phù hợp cho hạ tầng có sẵn, điều phối máy ảo và các luồng xử lý mẻ Cronjob truyền thống.
💎 4. KHI NÀO NÊN CHỌN DAGSTER?
ĐỀ XUẤT SỐ 1
🔄 Thay thế AWS Step Functions On-Premise: Pipeline phân nhánh nghiệp vụ phức tạp, xử lý hồ sơ, OCR theo State Machine.
☁️ Hạ tầng K8s Cloud-Native tinh gọn: Chỉ 3 service cốt lõi (Webserver, Daemon, Postgres nhẹ) + MinIO S3 (Zero NFS).
🧪 Kiểm thử tự động CI/CD 0.12s: Viết unit test in-memory bằng pytest trong RAM, tích hợp mượt mà GitLab CI PR.
🛡️ Bảo vệ chất lượng dữ liệu tại chỗ: Tích hợp Asset Checks (blocking=True) chặn đứng hóa đơn vượt ngân sách 100M.
🚀 Tóm lại: Nền tảng toàn diện nhất thay thế AWS Step Functions On-Premise, chuẩn hóa văn hóa phần mềm!
Thưa các anh chị, slide này tổng hợp toàn diện 4 trụ cột chiến lược khi chuyển dịch On-Premise: 1. Về hạ tầng On-Premise: Airflow đòi hỏi 6 thành phần cồng kềnh và đĩa chia sẻ NFS rất dễ nghẽn. Dagster kiến trúc Cloud-Native tinh gọn: 3 service cốt lõi, MinIO S3 và Pods K8s độc lập. 2. Về kiểm thử CI/CD: Airflow dính chặt database rất khó viết unit test. Dagster là pure function, test in-memory bằng pytest 4/4 tests chỉ mất 0.12 giây, tích hợp mượt mà vào GitLab CI. 3. Khi nào chọn Airflow: Khi cần điều phối hạ tầng chung, bật tắt máy ảo, trigger job Spark độc lập trên cụm server cũ có sẵn. 4. Khi nào chọn Dagster: Đề xuất số 1 để thay thế AWS Step Functions, xử lý nghiệp vụ tài chính/OCR phức tạp, cần bảo vệ chất lượng dữ liệu và chuẩn hóa văn hóa phần mềm.

Ma Trận So Sánh Kỹ Thuật Tổng Hợp (7 Tiêu Chí)

Tiêu Chí Kỹ Thuật Apache Airflow 2.x Dagster Đánh Giá
1. Triết lý thiết kế Task-Centric (Chạy tác vụ) Asset-Centric (Tài sản dữ liệu) Dagster thắng
2. Khả năng & Tốc độ Test Phụ thuộc DB, chậm, khó mock Pure Function, chạy Pytest trong RAM 0.05s Dagster vượt trội
3. Luân chuyển dữ liệu XCom nghẽn qua Database I/O Manager tách rời lưu trữ Dagster thắng
4. Kiểm soát chất lượng Tự viết task phụ rườm rà Asset Checks tích hợp (blocking=True) Dagster thắng
5. Cách ly hạ tầng (K8s) Chung tiến trình, dễ xung đột thư viện gRPC Out-of-process, cô lập hoàn hảo Dagster thắng
6. Hệ sinh thái & Connector Khổng lồ (hơn 10 năm phát triển) Trẻ hơn nhưng phát triển rất nhanh Airflow thắng
7. Trải nghiệm Developer Nhiều boilerplate, debug khó Chuẩn Software Engineering hiện đại Dagster thắng
Nhìn vào bảng tổng kết 7 tiêu chí: Airflow chỉ còn giữ ưu thế duy nhất về tuổi đời và số lượng connector có sẵn. Trên toàn bộ các khía cạnh về năng suất lập trình, khả năng kiểm thử, độ tin cậy dữ liệu và kiến trúc đám mây On-Premise, Dagster đều vượt trội hoàn toàn.

Định Vị Ứng Dụng & Hiện Thực Hóa On-Premise: Khi Nào Chọn Ai?

⚙️ KHI NÀO NÊN CHỌN APACHE AIRFLOW? Hạ Tầng Sẵn Có
  • Điều phối hạ tầng chung (Infra Orchestration): Bật/tắt máy ảo, trigger job dbt snapshot, gửi email cảnh báo, dọn log hệ thống định kỳ.
  • Tác vụ độc lập, thô (Coarse-grained Batch): Kích hoạt các job Spark, Trino, Flink chạy độc lập, không cần trao đổi dữ liệu phức tạp giữa các bước.
  • Đã có sẵn cụm On-Premise ổn định: Doanh nghiệp đã đầu tư hạ tầng VM/Celery với đội ngũ Ops quen vận hành 6 thành phần và ổ đĩa mạng NFS.
  • Kiểm thử chấp nhận mô hình truyền thống: Chấp nhận việc test gắn chặt với Database (dựng Docker Compose mất 3 - 5 phút/lần test).
📌 Tóm lại: Phù hợp cho hạ tầng có sẵn, điều phối máy ảo và các luồng xử lý mẻ truyền thống (Cronjob).
💎 KHI NÀO NÊN CHỌN DAGSTER? ĐỀ XUẤT SỐ 1
  • Thay thế AWS Step Functions On-Premise: Pipeline phân nhánh nghiệp vụ phức tạp, xử lý hồ sơ, OCR và đối soát tài chính theo State Machine.
  • Hạ tầng Cloud-Native K8s tinh gọn: Chỉ 3 service cốt lõi (Webserver, Daemon, Postgres nhẹ). Lưu trữ MinIO S3 nội bộ (loại bỏ hoàn toàn đĩa mạng NFS). Cô lập Pods qua gRPC.
  • Kiểm thử tự động CI/CD 0.12s: Viết unit test in-memory bằng `pytest` trong RAM, tích hợp mượt mà GitLab CI / GitHub Actions tự động kiểm thử trên từng Pull Request.
  • Bảo vệ chất lượng dữ liệu: Tích hợp sẵn Asset Checks (`blocking=True`) chặn đứng hóa đơn vượt ngân sách 100M ngay trong chu trình chạy.
🚀 Tóm lại: Nền tảng toàn diện nhất để thay thế AWS Step Functions trên On-Premise, chuẩn hóa văn hóa kỹ nghệ phần mềm cho đội Data!
Chúng tôi không nói Airflow tệ. Nếu công ty chỉ cần một công cụ kích hoạt dbt hay chạy job Spark hàng đêm trên cụm máy chủ cũ, Airflow vẫn dùng tốt. Nhưng với bài toán cốt lõi của chúng ta: thay thế AWS Step Functions trên hạ tầng On-Premise/Kubernetes, lưu trữ MinIO S3, cần kiểm thử CI/CD tự động 0.12s và bảo vệ chất lượng dữ liệu OCR tài chính, Dagster chính là sự lựa chọn số 1 của tương lai.

Lộ Trình Triển Khai 3 Giai Đoạn Lên On-Premise / K8s

Giai Đoạn 1 (Tháng 1 - 2)

Chuẩn Hóa & Pilot

  • Dựng cụm Dagster trên Kubernetes On-Premise bằng Helm Chart chuẩn.
  • Di chuyển 2 pipeline trọng điểm: OCR Hóa đơn PDF & Báo cáo đối soát chi phí.
  • Kiểm thử hiệu năng và độ ổn định.
Giai Đoạn 2 (Tháng 3 - 4)

CI/CD & Data Quality

  • Tích hợp bộ test pytest vào GitLab CI / GitHub Actions tự động.
  • Cấu hình I/O Manager kết nối kho MinIO nội bộ.
  • Đào tạo đội ngũ Data & Backend chuyển đổi tư duy sang Software-Defined Assets.
Giai Đoạn 3 (Tháng 5 - 6)

Chuyển Toàn Diện & Cắt AWS

  • Di chuyển 100% các luồng nghiệp vụ còn lại về On-Premise.
  • Tắt bỏ hoàn toàn các State Machine trên AWS Step Functions.
  • Tiết kiệm ~65% chi phí vận hành định kỳ hàng tháng!
Cam Kết Bảo Đảm

Quá trình chuyển dịch chạy song song (Parallel Run) trong 2 tuần đầu để đối chiếu độ chính xác 100% trước khi ngắt kết nối hệ thống cũ, đảm bảo không có gián đoạn kinh doanh.

Lộ trình di chuyển được thiết kế an toàn trong 3 giai đoạn, không gây gián đoạn hệ thống hiện tại. Việc chuyển dịch này vừa giúp doanh nghiệp làm chủ dữ liệu trên On-Premise, vừa nâng cao chất lượng code của đội ngũ kỹ sư lên chuẩn mực kỹ nghệ phần mềm chuyên nghiệp.
